## 15. LIMITATIONS

1. The planner does **not** read `process.env`, so `env_gate_satisfied` is conservatively reported as `false` in the status JSON. A real orchestrator (future phase) would verify the env var externally.
2. The `wait_for_human_approval` stage is conceptual only — there is no UI/CLI for it yet. A future phase would need to implement this.
3. The `one_shot_promote` and `rollback_if_human_approved` stages are gated by env var + confirm phrase but not actually wired to a loop. They would only fire under explicit manual invocation.
4. The 27-check validator uses precise regex patterns to avoid false positives from property names like `no_child_process: true` (a property flag) vs actual `child_process` module usage.
5. The new GET endpoint auto-generates the status JSON on-the-fly if the file is missing, but for production use the planner should be run explicitly first to write the file.
